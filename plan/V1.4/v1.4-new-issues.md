# PetAgent V1.4 New Issues

**Date:** 2026-05-28
**Project path:** `/Users/wylam/Documents/workspace/Petagent`
**Scope:** New issues and design questions discovered after V1.3. Keep these
separate from V1.3 to avoid mixing old fast-reply fixes with the next design
cycle.

## Product Direction

V1.4 should improve 豆豆 from the user's point of view:

- fast conversations must show visible pet action changes;
- the action set should feel like a small cat companion, not a generic loading
  indicator;
- memory should feel present in quick mode without making quick mode slow;
- memory files should be easier to reason about;
- background memory work must not block reply text or voice playback.

## Issue 1: Fast Reply Action Is Not Visibly Stable

### Symptom

During quick conversations, 豆豆 often does not visibly change action even when
the model returns a fast `action`.

### Current Code Evidence

- Fast responses can include `action`, and `BehaviorDirector.onBackendResponse`
  prioritizes it.
- `App.applyPetResponse()` applies that action, then immediately enters
  `waiting_voice` when `audio_job_id` exists.
- `waiting_voice` and `speaking` currently force phase actions such as
  `review`, which can overwrite the fast action before the user perceives it.

### UX Problem

The user experiences 豆豆 as frozen or always in the same "thinking/speaking"
state. This weakens the feeling that 豆豆 understood the message emotionally.

### Candidate Direction

- Preserve a fast action long enough to be perceived before switching to voice
  phase visuals.
- Add explicit phase-aware actions, for example `speak`, instead of forcing
  every audio phase into `review`.
- Define whether one-shot actions can complete before playback starts, or
  whether they blend into a speaking loop.

### Open Decision

Decide the front-end rule:

1. fast action plays first for a short minimum duration, then voice phase starts;
2. fast action is mapped into a speaking-compatible action immediately;
3. text bubble shows immediately, audio queues in parallel, sprite keeps the
   action until playback begins.

## Issue 2: Current Sprite Action Set Is Too Small

### Symptom

The current sprite action list has only nine actions:

- `idle`
- `waiting`
- `review`
- `waving`
- `jumping`
- `failed`
- `running`
- `running-left`
- `running-right`

### UX Problem

Many different conversational states collapse into the same few actions. This
makes 豆豆 feel less alive, especially in fast mode where one action is the main
nonverbal feedback.

### Candidate V1.4 Action Vocabulary

Define the action vocabulary before generating or integrating new assets:

| Action | User-facing meaning | Typical use |
| --- | --- | --- |
| `idle` | calm breathing | default resting |
| `greet` | greeting | "早上好", "在吗" |
| `happy` | pleased response | praise, light agreement |
| `listen` | attentive listening | recording / user talking |
| `think` | short thought | quick internal wait |
| `speak` | talking | audio playback |
| `remember` | writes to notebook | explicit memory trigger |
| `comfort` | gentle comfort | sad/tired/stressed user |
| `confused` | unsure / did not hear | ASR low confidence |
| `sleepy` | sleepy | night, low energy |
| `deny` | soft refusal / dislike | "不要", overpoke recovery |
| `excited` | high energy | good news, playful moment |

### Asset Direction

New sprite assets can be generated after the action contract is fixed. Any
generation workflow must preserve:

- transparent background;
- consistent 豆豆 identity;
- fixed cell size, preferably keeping the existing `192x208` cell unless a
  separate art-system migration is approved;
- loop vs one-shot metadata;
- bounded atlas size for Nubia WebView performance.

Do not generate assets before the action list and animation metadata are
approved.

## Issue 3: `user.md` And `memory.md` May Be Over-Split

### Symptom

Memory is currently split across:

- `backend/data/memory_cards/user.md`
- `backend/data/memory_cards/memory.md`

Fast Reply currently selects a tiny amount of memory from both files.

### UX Problem

The split is harder to reason about, and quick mode can feel like it remembers
too little. The user-facing model would be simpler if there is one notebook.

### Candidate Direction

V1.4 should consider making one canonical file:

```text
backend/data/memory_cards/memory.md
```

Categories carry the distinction that `user.md` used to provide:

- `identity`
- `preference`
- `relationship`
- `project`
- `temporary`

Compatibility aliases may remain internally for migration or old tests, but new
prompt memory should read one canonical notebook.

### Open Decision

Confirm whether `user.md` should be physically deprecated or only hidden behind
a merged read API for one release.

## Issue 4: Fast Mode Memory Budget Is Too Thin

### Symptom

Fast Reply currently uses at most one selected `user.md` item and one selected
`memory.md` item.

### UX Problem

Quick mode may feel fast but shallow. 豆豆 can fail to reference enough stable
preference, relationship, or project context.

### Candidate Direction

Fast mode should load up to 10 short memory lines from the canonical notebook,
while still staying deterministic and cheap.

Proposed selection:

1. up to 2 `identity` lines;
2. up to 3 `preference` lines;
3. up to 3 recent `relationship/project` lines;
4. up to 2 fresh `temporary` lines;
5. total prompt budget capped at about 600-800 Chinese characters.

Fast mode still must not load:

- current time;
- device state;
- dynamic retrieval;
- SQLite scored memories;
- summaries;
- tools.

## Issue 5: Memory Should Be Summarized After Each Conversation Turn

### Requested Direction

After every conversation round, schedule a background memory summarization call.
The current reply and audio must not wait for this job.

### Candidate Provider

Use MiMo through OpenAI-compatible chat completions:

- base URL from `MIMO_BASE_URL`, expected value:
  `https://api.xiaomimimo.com/v1`
- API key from `MIMO_API_KEY`
- model: `mimo-v2.5`

Do not hard-code API keys in code, specs, tests, or committed files.

### Candidate Memory Summarization Contract

Inputs:

- current canonical `memory.md`;
- latest user input;
- latest 豆豆 reply;
- route (`fast_reply` or `thinking`);
- optional memory trigger category.

Output should be operations, not file text:

```json
{
  "add": [
    {
      "category": "preference",
      "content": "主人更喜欢豆豆快速回应，但不要显得变笨。"
    }
  ],
  "update": [],
  "delete": []
}
```

Backend validates and applies operations. The model must not write files
directly.

### Safety Rules

- Keep at most 10 active memory lines in the fast prompt, not necessarily only
  10 lines on disk unless that is approved.
- Reject secrets, tokens, passwords, and raw API keys.
- Reject long copied chat excerpts.
- Reject permanent negative labels about the user.
- Deduplicate near-identical memory content.
- If summarization fails, skip silently and keep the user-facing turn complete.

### Performance Rule

The memory summarizer must run after response persistence and audio enqueue. It
must not hold dispatcher locks, audio job locks, or notebook locks during the
LLM call.

## Issue 7: Fast Voice ASR Shows "Not Very Good At Recognition"

### Symptom

When the user speaks to 豆豆, the frontend repeatedly shows
"语音识别暂时不太灵，但豆豆还在听。"

### Current Code Evidence

- `VoiceButton.tsx` shows that copy only when
  `voice_route.fallback_reason` is `asr_provider_error` or
  `asr_provider_exception`.
- Fast voice maps ASR provider errors to a local recovery reply instead of
  running the heavier thinking/audio-understanding route.
- Real local ASR probes showed `FunAudioLLM/SenseVoiceSmall` and
  `iic/SenseVoiceSmall` intermittently returning `asr_http_500`.
- `TeleAI/TeleSpeechASR` was slower by several hundred milliseconds but passed
  repeated real probes more consistently.

### UX Problem

The user experiences this as 豆豆 hearing the button press but failing the
conversation. Retrying only after the user sees an error is worse than spending
roughly one extra second on a more stable fast ASR path.

### Fix Direction

- Prefer the more stable `TeleAI/TeleSpeechASR` for fast voice ASR.
- Keep SenseVoice models as transient 5xx fallbacks.
- Retry only quick transient provider/server failures, not slow timeouts,
  malformed JSON, auth errors, or client/config errors.
- Keep fast voice within the frontend request budget; do not silently promote
  fast voice to thinking mode on ASR failure.

### Nubia Acceptance

Pass requires a real `/api/voice/chat` upload on Nubia to return HTTP 200 with:

- `voice_route.selected = "fast_reply"`;
- non-empty `user_text`;
- empty `voice_route.fallback_reason`;
- empty `voice_route.asr_error_code`;
- a normal reply and audio job.

## Issue 8: Nubia Voice No-Reply From Half-Alive Runtime

### Symptom

The user sent voice from the Nubia frontend and 豆豆 did not reply. Related
frontend messages included "声音刚刚没出来" and repeated retry prompts.

### Root Cause Evidence

Recent Nubia database rows showed the backend had completed voice turns and the
TTS audio jobs reached `ready`, but the user still saw no reply. During the
failure window, the runtime process and port were alive while `/api/health`,
`/api/runtime/client-config`, and audio-job polling accepted connections without
returning responses.

The stuck process held a zero-byte routine backup file under
`backend/data/backups/`, and the runtime log contained
`sqlite3.OperationalError: database table is locked`. The old maintenance layer
also ran WAL checkpoint/truncate paths from the background worker and deep
health.

The Termux service manager made the failure harder to recover from because it
started `scripts/start.sh` with `PETAGENT_FOREGROUND=1`. That foreground uvicorn
process replaced the manager loop, so the manager could not keep checking health
or restart a half-alive runtime.

### UX Problem

From the user's point of view this looked like 豆豆 heard the voice button but
then went silent. The backend may have finished the reply later, but the frontend
could time out or lose audio polling while the server was half-alive.

### Fix Direction

- Keep SQLite persistence, because it still stores pet state, raw events,
  audio jobs, agent-run diagnostics, device state, activation state, incidents,
  and memory queues.
- Delete the redundant online SQLite backup/WAL maintenance layer that created
  lock contention on the old Nubia.
- Keep health checks lightweight; deep health must not mutate WAL state.
- Make the Termux service manager run as a real manager and restart repeated
  HTTP half-alive states even when process and port are still present.
- Deploy by clearing remote code directories before unpacking, so deleted files
  do not remain on the phone.
- Increase frontend voice request timeouts to match real ASR + LLM + TTS
  latency budgets.

### Nubia Acceptance

Pass requires:

- no runtime references to the removed online backup/WAL checkpoint code;
- remote `backend/app/runtime/backup.py` absent after deploy;
- `/api/health`, `/api/health/watchdog`, and `/api/health/deep` return quickly;
- a real Nubia `/api/voice/chat` upload returns text, route/action, and an
  audio job;
- the audio job reaches `ready`;
- `backend/tests/test_live_nubia.py` passes against the connected Nubia.
