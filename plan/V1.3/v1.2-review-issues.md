# PetAgent V1.3 Issue Intake: V1.2 Review Findings

**Date:** 2026-05-25
**Source:** Post-V1.2 spec/code review and Nubia live diagnosis
**Scope:** Issues found after PetAgent V1.2 Doudou sprite migration.

## Context

V1.2 completed the visible migration from kaomoji Momo to sprite-based cat
豆豆. The main user-visible experience works, and the Nubia backend was
confirmed healthy after reconnecting network. However, the review found several
gaps between the original V1.2 spec and the current implementation. These
should be treated as V1.3 intake items.

## Issue 1: Sprite Tap Still Calls The Slow LLM/TTS Event Path

### Symptom

Tapping 豆豆 feels local because the sprite reacts immediately, but the frontend
still sends `postPetEvent("pet_head")` in the background.

### Evidence

- `frontend/src/App.tsx`
  - `handleDoudouTap()` calls `director.onTap()` for the local animation.
  - The same handler then calls `postPetEvent("pet_head")`.
- `frontend/src/pet/api.ts`
  - `postPetEvent()` posts to `/api/pet/event`.
- `backend/app/api/pet.py`
  - `/api/pet/event` calls `dispatcher.handle_event(payload)`.

### Why This Is A Problem

The V1.2 spec explicitly required ordinary taps to stay off the blocking
`/api/pet/event` path:

- tap should update local visible state within 100ms;
- tap should not set global `busy=true`;
- tap should not wait for or trigger LLM/TTS/audio jobs;
- backend sync, if present, should be deterministic and low priority.

Current code does not block the local animation, but it can still enqueue
provider work in the background. This can waste tokens, occupy the TTS queue,
create unexpected speech, and make basic petting depend on provider/network
health.

### Suggested Fix

Pick one of these:

1. Do not sync ordinary sprite taps to the backend in V1.3.
2. Add a lightweight endpoint such as `/api/pet/reaction` that records state/log
   updates without LLM or TTS.
3. Extend `/api/pet/event` with an explicit local-reaction mode and test that it
   does not call LLM or enqueue audio jobs.

Recommended: add a dedicated lightweight endpoint, because it preserves state
sync while making the fast-path boundary explicit.

### Verification

- Frontend test: tapping sprite updates bubble/sprite immediately and does not
  call `/api/pet/event`.
- Backend test: lightweight tap endpoint updates deterministic state/log only.
- Backend test: lightweight tap endpoint does not call LLM and returns no
  `audio_job_id`.
- Nubia smoke: repeated tapping does not create audio jobs.

## Issue 2: Behavior Plan Slots Are Validated But Not Actually Executed

### Symptom

The backend and frontend can validate `behavior_plan`, but the frontend mostly
uses only the first step. Steps assigned to `before_speech`, `speech`,
`after_speech`, and `idle_after` are not consistently advanced at phase
boundaries.

### Evidence

- `frontend/src/pet/behaviorDirector.ts`
  - `onBackendResponse()` validates/falls back a plan and stores it in
    `queuedSteps`.
  - It immediately returns only the first step's action.
  - `advanceSlot(slot)` exists.
- `frontend/src/App.tsx`
  - `applyPetResponse()` calls `onBackendResponse()`.
  - `playResponseAudio()` changes phases to `waiting_voice`, `speaking`, and
    `idle`, but does not call `advanceSlot()`.

### Why This Is A Problem

V1.2 intended model-selected behavior plans to be a small performance layer:

- `before_speech`: after text response arrives, before audio playback starts;
- `speech`: while TTS is pending or audio is playing;
- `after_speech`: after audio ends or text-only response is displayed;
- `idle_after`: final transition when no protected phase is active.

Current behavior cannot reliably express those stages. A plan like
`failed -> waving -> jumping -> idle` may collapse to only `failed`, then be
overridden by audio phase handling.

### Suggested Fix

Wire `BehaviorDirector.advanceSlot()` into `App.tsx`:

- call `before_speech` after `applyPetResponse()` receives a response;
- call `speech` when entering `waiting_voice` or `speaking`;
- call `after_speech` after audio playback ends, or immediately for text-only
  replies after the response is shown;
- call `idle_after` before settling back to idle, unless a protected phase is
  active.

Also decide how one-shot duration interacts with phase transitions. Keep phase
actions authoritative for `listening`, `waiting_voice`, and `speaking`.

### Verification

- Unit test: a plan with all four slots advances in the expected order.
- App test: a text response with `before_speech`, `speech`, and `after_speech`
  causes corresponding sprite actions around audio job polling and playback.
- App test: protected phases still override unsafe plan actions.

## Issue 3: Frontend PetResponse Type Is Missing Behavior Fields

### Symptom

The backend response includes optional `behavior_intent` and `behavior_plan`,
but the frontend `PetResponse` type does not declare them.

### Evidence

- `backend/app/runtime/actions.py`
  - `PetResponse` includes `behavior_intent` and `behavior_plan`.
- `frontend/src/pet/types.ts`
  - `PetResponse` does not include either field.
- `frontend/src/App.tsx`
  - casts the response to `Record<string, unknown>` to read both fields.

### Why This Is A Problem

This weakens the API contract and makes frontend code less reliable. TypeScript
cannot catch behavior-plan shape regressions, and future refactors may drop the
fields accidentally.

### Suggested Fix

Add frontend types:

- `DoudouAction`;
- `DoudouBehaviorSlot`;
- `DoudouBehaviorStep`;
- optional `behavior_intent` and `behavior_plan` on `PetResponse`.

Reuse or re-export the existing types from `doudouBehaviorPlan.ts` to avoid
duplicating incompatible definitions.

### Verification

- `npm test` or targeted frontend type/test run.
- Remove `Record<string, unknown>` casts in `App.tsx`.

## Issue 4: Failed Audio Job Retry Does Not Re-Synthesize Audio

### Symptom

When a TTS job fails because the phone is offline, the UI shows "声音刚刚没出来".
After network returns, pressing "重试发声" only re-checks the same failed job.
It does not create a new TTS job.

### Evidence

- `frontend/src/App.tsx`
  - `handleRetryAudio()` calls `getAudioJob(lastAudioJobId)`.
  - If the job is still failed/expired, the UI remains in audio error.
- Nubia diagnosis on 2026-05-25:
  - `aud-5b009e074af7`, `aud-68c23d051add`, and `aud-9597da80d2e5` were
    `failed`.
  - Error: `ProviderNetworkError` for
    `token-plan-sgp.xiaomimimo.com/v1/chat/completions`.
  - The device had no default route at the time.

### Why This Is A Problem

This is confusing for normal recovery. The user can reconnect network, but the
UI retry cannot recover because the failed job is terminal. The only working
manual recovery is to send a new message.

### Suggested Fix

Add a true retry path:

1. Backend stores enough audio job metadata to retry synthesis: reply text,
   voice style, run id, event id, and session id.
2. Add an endpoint such as `POST /api/audio/jobs/{job_id}/retry`.
3. The endpoint creates a new audio job from the old job's text/style if the old
   job is terminal failed/expired.
4. Frontend `handleRetryAudio()` calls retry for failed/expired jobs and then
   polls the new job id.

Keep the existing simple poll path for pending jobs.

### Verification

- Backend test: retrying a failed job enqueues a new job with same text/style.
- Backend test: retry refuses non-terminal jobs or unknown ids.
- Frontend test: `audio_error` retry receives a new `audio_job_id` and plays it.
- Nubia smoke: disconnect network, trigger audio failure, reconnect network,
  press retry, confirm audio becomes ready.

## Issue 5: Audio Error Copy Hides Root Cause

### Symptom

The UI always shows "声音刚刚没出来" for audio job failure, regardless of whether
the cause is network, provider auth, timeout, expired job, or browser playback
failure.

### Evidence

- `frontend/src/App.tsx`
  - `playResponseAudio()` catches all audio failures and sets
    `setBubbleText("声音刚刚没出来。")`.
- Audio job API includes `error`, but the frontend does not classify it for
  user-facing recovery guidance.

### Why This Is A Problem

During the Nubia issue, the real problem was no network route. The UI message
made it look like a recorder or speaker problem. This slowed diagnosis.

### Suggested Fix

Map audio job failures to quiet, actionable messages:

- network/provider connection: "网络刚刚没连上，豆豆发不出声音。";
- provider timeout: "声音生成太慢了，等一下再试。";
- provider auth/quota: "发声服务配置可能有问题。";
- playback failure: "声音生成了，但浏览器没播出来。";
- unknown: keep existing generic copy.

Do not expose raw provider error strings in the UI.

### Verification

- Frontend tests for error-class/message mapping.
- Backend may optionally add `error_class` to audio job responses.

## Issue 6: Nubia Network/Proxy Recovery Is Not Visible Enough

### Symptom

On 2026-05-25, the Nubia device had:

- `wlan0` without carrier and down;
- `rmnet_data0` down;
- no SIM;
- `ip route get 1.1.1.1` returned network unreachable;
- `token-plan-sgp.xiaomimimo.com` could not resolve;
- proxy port `7897` was not listening.

The service manager logs did contain repeated network warnings and stale
frontend heartbeat relaunches, but the frontend did not make the network cause
obvious.

### Why This Is A Problem

The backend can remain healthy while provider calls fail. The UI currently
checks browser online status, but on Android/WebView this may not map cleanly to
Termux provider connectivity. The user sees a pet error rather than a device
network error.

### Suggested Fix

Add a lightweight backend/provider connectivity indicator for the frontend:

- expose a safe public summary in `/api/runtime/client-config` or a new
  `/api/runtime/status` endpoint;
- include recent audio/provider failure class and provider connectivity age;
- avoid secrets and raw URLs.

Alternatively, keep this as a debug-only tool if product UI should stay quiet.

### Verification

- Nubia smoke with Wi-Fi off: frontend shows a quiet network-specific message
  after provider failure.
- Health/watchdog remains light and non-blocking.

### Why This Is A Problem

not leave it untracked.

### Verification

## Confirmed Non-Issue: Audio Failure Was Not Caused By Sprite Migration

The "声音刚刚没出来" incident during review was caused by device network state,
not by the Doudou sprite renderer or browser audio playback.

Evidence after reconnecting network:

- `ip route get 1.1.1.1` returned a route via `wlan0`.
- `ping 1.1.1.1` succeeded.
- TTS domain returned HTTP response headers.
- A new text smoke test returned `audio_job_id=aud-1aadf120084f`.
- That job became `ready`.
- Generated URL:
  `/static/audio/reply-20260525-122221-ea83a6f0.wav`.
- Static audio URL returned `200 OK`, `content-type: audio/x-wav`,
  `content-length: 122924`.

## Recommended V1.3 Order

1. Fix sprite tap fast-path boundary.
2. Add true audio job retry and better audio error classification.
3. Wire behavior-plan slots into the actual frontend phase lifecycle.
4. Complete frontend response typing.
5. Add focused tests and Nubia smoke checks.
6. Clean up untracked V1.2 stage documentation.
